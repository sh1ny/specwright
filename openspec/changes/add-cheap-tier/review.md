## Findings

### Moderate

**M1. The settings parser already reads `yes` as `true`, so the "`yes` is off with a note" scenario fails unless `tier` reads the raw text. That differs from every other boolean setting.**
- D2 says `pr-pair.sh tier` "loads the settings with the existing `load_settings`". `load_settings` → `parse_yaml` → `scalar()` returns `True` for `true` and `yes` (any case), and `False` for `false` and `no` (`pr-pair.sh:372-375`). After parsing, `enabled: yes` cannot be told apart from `enabled: true`. A straightforward implementation therefore prints `"cheap_tier": true` for `yes`. That fails the cost-tiers scenario "An unrecognised value is off and reported". The raw text exists: `Map.text[key]` keeps each plain scalar as written (`pr-pair.sh:429-433`, `parse_yaml` line 467), and `setting_text` already reads it. Neither the design nor the spec says to use it.
- The rule also departs from the rest of the settings. `pr.react: yes` is on (`bool(pr.get("react"))`, `pr-pair.sh:588`), and `pr.delete_branch: yes` passes the agent-merge `isinstance(delete, bool)` check (`pr-pair.sh:603-605`). D2 rejects having apply read the YAML because an agent "can read `yes` as on". The project's own parser does the same. One of the two has to give, and the design should say which: either `tier` compares `Map.text["enabled"]` with `true` (and a quoted `"true"`, which parses to a string, is off), or `yes` counts as on like every other boolean and the scenario changes.
- Related gap: `cheap_tier: true` (a scalar, not a map) makes a naive `s.get("cheap_tier").get("enabled")` raise. The result is a non-zero exit, so apply reports "could not be read" instead of the unrecognised-value note. State what `tier` prints for a non-map `cheap_tier`.

**M2. The spec scenario "Ready after a quiet wait with check progress" cannot happen as written, so its one-test-per-scenario cannot be built from it.**
- With `--until attention`, a poll is filtered only while `checks.pending > 0` (D3). The scenario's WHEN is "a wait times out after skipping a check that went from pending to pass, and the snapshot then meets every other ready condition". Ready needs `checks.pending` 0 (watch step 3). Suppose a check goes from pending to pass and nothing else is pending. That poll has `pending == 0`, so it wakes `changed`, not `timeout`. Suppose instead others are still pending. Then they must finish before the snapshot can be ready, and that poll wakes `changed` too. The sig is compared with the baseline on every poll (`pr-snapshot.sh:531`).
- The only way to reach `timeout` with `filtered > 0` and a ready snapshot is this: the baseline is already all-pass, a check is re-run (pass → pending, filtered), and it passes again, so the sig equals the baseline once more. That is a re-run that ends where it started, not "a check that went from pending to pass". As worded, the scenario leads a test writer either to a fixture that contradicts D3 or to a test that does not match its scenario.
- The Failure table promises "one [test] per spec scenario". Reword the scenario to the re-run case, which is the only behaviour the timeout rule changes. Otherwise drop the clause and say that a ready PR still needs the full wait after the last check's `changed` wake, as today.

**M3. "Each task group goes to the light implementer" conflicts with the kept "small groups you may implement directly" clause, and the dispatch trial may show no dispatch at all.**
- The cost-tiers requirement says apply "SHALL send each task group of a change whose `design.md` has `TIER: LIGHT` to `specwright-implementer-light`". The apply DELEGATION text the design edits (`schema.yaml:489-501`) keeps "Small groups (one or two trivial edits) you may implement directly". LIGHT changes are by definition the doc edits, template blocks and version bumps (proposal, Why) that fit that clause. So with the tier on, the orchestrator may still do every group itself on the expensive model. The requirement's SHALL is then not met, and the saving does not appear.
- D4's evidence is "a LIGHT apply in a scratch project with the cheap tier on, with the harness transcript showing `specwright-implementer-light`". The add-greeting fixture's groups are two one-function tasks and one README line (`fixtures.py`, `change_artifacts`). An orchestrator following the clause may never dispatch, and the trial would show nothing.
- Decide one way and write it into both the requirement and the DELEGATION edit. Either the small-group exception does not apply to a LIGHT change with the tier on, or the requirement says "each delegated group" (as its scenarios already do). With the second option, D4's trial must use a change whose groups are not small, or must tell the orchestrator to delegate.

**M4. The reworded exit criterion makes the stress tier a close gate that D4 calls a diagnostic, and it has no exit for a gap that wording cannot fix.**
- D5 and the proposal reword the M4 criterion to include "stress-tier parity on Haiku". D4 says the stress tier "measures whether Haiku can follow the text, not a shipped setup", that `tiers.py` "is diagnostic, not a CI gate", and that each gap is fixed and re-run "before the record is final". The Mechanism Ledger rejects a CI gate for the same reason.
- The stress kinds `watch` and `light-apply` put Haiku in the orchestrator's seat. Evals 55, 56 and 64 run the whole agent-merge, cleanup, release-auto and roadmap-offer flow (`evals.json` ids 55/56/64), and eval 3 runs the specwright-commit apply flow. The cost-tiers spec rules out that configuration for real use. If Haiku misses an assertion through capability rather than wording, no skill edit closes the gap, and M4 close then reports the criterion failing. With one run per configuration, a single noisy base or Haiku run is also a "difference" (exit 1). Nothing says whether parity means `tiers.py` exit 0 or a reviewed record.
- Write the criterion's exact text in D5 so that it matches D4. For example: "the stress run is recorded in `stress.md`, every difference is either fixed in the wording and re-run, or listed with the reason it is not a wording gap". Or keep strict parity and add the rule for an unfixable difference (record and accept it, file an issue, or narrow the kinds). As written, the change can ship 0.8.0 and still leave its milestone unclosable.

### Suggestions

- **S1.** Output shape: the spec says `tier` prints `{"cheap_tier": true|false}` (plus `note`), and D2 says `{"ok": true, "cheap_tier": bool}`. Pick one, because the skill-text and script tests will assert on it. (Re-check: resolved; both now say `{"ok": true, "cheap_tier": bool}` plus any `note`.)
- **S2.** Apply's instruction lives in `schema.yaml`, not in `specwright-pr`. Write the call there as `bash <specwright-pr>/scripts/pr-pair.sh tier --code <toplevel>`, with `<specwright-pr>` being that skill's folder, as specwright-commit, -finish and -branch already do for `as.sh`. A bare `scripts/pr-pair.sh` resolves against the wrong folder during apply and turns the tier off through the failure row. (Re-check: resolved in D2.)
- **S3.** The body-equality test compares only the body and `model:`. The light implementer's `tools:` line (and OMP's `spawns:`) can drift without the test noticing. T6's "No" rests on the light implementer having "the same tools as the current one". Compare the frontmatter too, with only `name`, `description` and `model` allowed to differ. (Re-check: `tools:` added to D1 and the spec; OMP's `spawns:` is still not named.)
- **S4.** D1/README for OMP: both agents use the `pi/smol` role, so mapping roles in `~/.omp/agent/config.yml` cannot separate them. The user has to edit the `model:` line of the installed `specwright-implementer.md` to another role. `carry_model` keeps that edit across updates (`update.sh:1619-1627`). Say that in the README instead of "maps the implementer to a stronger role". (Re-check: resolved in D1.)
- **S5.** Context's "one orchestrator turn per finished check" overstates the saving. Polls run every `--interval` (300 s by default), so checks that finish within one interval cost one wake. The saving is one wake per poll interval in which a check changed, minus the final one. That is still real, but the Context and Risks text should use that figure. (Re-check: resolved in Context.)
- **S6.** Flow gap to add: when watch handles a failing check with `gh run rerun --failed` and restarts the wait right away, the new baseline can still list that check as failing. If the re-run fails again while other checks are pending, it is filtered as "already failing in the baseline" until CI ends. Today it would wake at once. That is bounded and arguably fine, but it should be listed beside the existing "fails, then re-run" gap. Also state what `--until` without `--wait` does: exit 2, or ignored. (Re-check: resolved; Flow & State Gaps and D3/pr-watch spec now cover both.)
- **S7 (re-check, non-blocking).** D2's second Rejected line still gives as its reason that "an agent can read `"true"` or `yes` as on". After M1, `yes` is on by rule, so reading it as on is correct. Drop `yes` from that reason (keep `"true"`, `on` or a number), and likewise in the Mechanism Ledger row for `pr-pair.sh tier`.
- **S8 (re-check, non-blocking).** D3's "A `timeout` after filtered polls is only reachable when the checks end where the baseline had them" is too strong. A wait whose CI outlasts `--timeout` also times out after filtered polls, with checks still pending (so not ready). Qualify it as "A `timeout` after filtered polls with no check pending is only reachable when ...". The pr-watch scenario itself is correct.
- **S9 (re-check, non-blocking).** proposal.md line 26 still summarises the criterion as "stress-tier parity on Haiku", while D5's exact text no longer requires parity (`tiers.py` exit 0 is not required). Align the proposal's summary with D5 so the two do not read as different criteria.
- **S10 (re-check, non-blocking).** For a flow-map form (`cheap_tier: { enabled: "true" }`), `scalar()` returns a plain `dict`, not a `Map`, so there is no `text` to quote in the note's "<text as written>" (`pr-pair.sh:362-367`). Say the note falls back to the parsed value there, or test only the block form.

## Required Changes

1. **M1:** In D2 and the cost-tiers requirement "The cheap tier is off unless enabled", state how `tier` decides. Either it compares the raw text (`Map.text["enabled"]`) with `true`, so `yes`, `True` and a quoted `"true"` are off with a note, and the requirement says this deliberately differs from `pr.react` and the other booleans. Or `yes` counts as on like the other booleans, and the `yes` scenario is rewritten with a value the parser leaves as a string (for example `on`). Also state what `tier` prints when `cheap_tier` is not a map.
2. **M2:** In the pr-watch requirement "Watch waits for attention", replace the scenario "Ready after a quiet wait with check progress" with the reachable case. The baseline is all-pass, a check is re-run (pass → pending, filtered), and it passes again before the timeout. Watch then treats the `timeout` wake as a full wait with no new activity. Otherwise drop the timeout clause and its scenario. Fix D3's last sentence to match.
3. **M3:** Make the cost-tiers requirement "A LIGHT change's groups go to the cheap implementer" and the DELEGATION edit agree on the small-group clause, choosing one of the two options in M3. If small groups may still be done inline, D4's dispatch trial must state how a dispatch is guaranteed: a fixture with a non-trivial group, or an instruction to delegate.
4. **M4:** In D5, give the exact new text of the M4 cheap-tier exit criterion. Make it consistent with D4's "diagnostic" framing, and say what closes the criterion when a Haiku difference is not a wording gap (and whether `tiers.py` exit 0 is required).

### Re-check of Required Changes

1. **M1: applied.** The second option was taken. D2 decides on the parsed value: a parsed `True` (`true`, `yes`) is on, a parsed `False` or a missing key is off, and anything else (`on`, a quoted `"true"`, a number) is off with a note quoting the text as written. The cost-tiers requirement says the same ("`true` or `yes`, like the other boolean settings"). The scenario now uses `on`, which `scalar()` returns as the string `"on"` (`pr-pair.sh:372-380`), so it is reachable. A non-map `cheap_tier` is off with the note `cheap_tier must hold enabled: true|false; treated as false` (D2), with its own scenario "The section is not a map". Leftover rationale wording is S7 and S10 (non-blocking).
2. **M2: applied.** The pr-watch scenario is now "Ready after a quiet wait with a check re-run": baseline all-pass, one check re-run (pass → pending, filtered), passes again before the timeout. This is consistent with D3's filter (`attn` same, `pending > 0`, no new failure), and the final sig equals the baseline, so the wait wakes `timeout`. D3's closing sentences were rewritten to match. The overstatement in one of them is S8 (non-blocking).
3. **M3: applied.** The first option was taken. The requirement says every group of a LIGHT change goes to `specwright-implementer-light` with the tier on, "small groups included (no inline exception)", and its scenario names "a one-edit group included". D4 states that the DELEGATION small-group clause (`schema.yaml:502`) applies only when the tier is off or the change is FULL, and that this is what guarantees the dispatch trial dispatches. A FULL change keeps today's rule. No contradiction with the FULL or fallback scenarios.
4. **M4: applied.** D5 gives the exact criterion text: dispatch shown by the trial in `stress.md`, dispatch unchanged with the tier unset, watch on `--until attention`, and every difference `tiers.py` reports either fixed in the wording or recorded in `stress.md` as a model limit with its evidence. It says `tiers.py` exit 0 is not required, and that a difference that is not a wording gap closes the criterion once it is recorded with a re-run after a wording attempt. That matches D4's "diagnostic, not a CI gate" and "fixed ... and re-run before the record is final". The proposal's one-line summary still says "parity" (S9, non-blocking).

All four Required Changes are applied. The edits introduce no contradiction in normative text (requirements, scenarios, D-choices). S7-S10 are wording follow-ups in rationale and summary text, and none of them blocks apply.
