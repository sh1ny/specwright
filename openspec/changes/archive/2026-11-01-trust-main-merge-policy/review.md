## Findings

### Critical (blocking)

None.

### Moderate

1. **(Round 2) D6 checks both snapshots against one reviewed head, so store-backed pairs can never pass `reported.*.store`.** D1's interface takes one `--head <sha>` (the code PR's head, used for the code repository's contents read) and one optional `--reviewed-head <sha>`. D6 sets `ok` true "only when the snapshot's `head_oid` is the reviewed head", where "the reviewed head is `--head`, or `--reviewed-head <R>`". Flow & State Gaps, "Store-backed pair", passes both PRs' snapshots to one `policy --store` call. The store snapshot's `head_oid` is the store PR's head (pr-snapshot.sh:382, `head_oid: $p.headRefOid`), a commit in another repository, and it never equals the code head. So `reported.main.store` is always `head_mismatch`. D6 then restarts the store PR's wait with `reviewer_args` and returns to step 1, and the next pass fails the same way. A store-backed change with `pr.merge: agent` never merges and loops on review re-requests. The archive carry-over has the same problem in the other direction. For a store-backed change the archive commit lands on the *store* branch (SKILL.md watch step 3, "the archive commit is on the store branch"). So the head that `archive-only` judged, and the pre-archive head `R`, are store commits, while `--head` and the single `--reviewed-head` are interpreted against the code snapshot too. This fails closed and merges nothing, but it breaks a shipped capability ("Store-backed changes merge as a pair", main spec) and costs a review request per loop. No scenario in the delta covers a store-backed pair, so tests written from the spec would not catch it. **Re-check: resolved by Required Changes 1 and 2.**

2. **(Re-check R1) An edit outside the Required Changes: D6 restarted the wait with the head's reviewers, and posted their requests, before the user had said yes.** The first re-check found in D6: "When the head's `pr.merge` is `agent` but `reported.head` is not `ok`, watch asks nothing yet: it restarts the wait with the head's `reviewer_args` and asks once the head's reviewers reported (D2)." That sentence let anyone who can push to the PR branch make watch post request text from the remote head under the maintainer's or `request_as` account before any user decision (`review_requests`, pr-pair.sh:631-637; SKILL.md:55), and it conflicted with D2. **Second re-check: resolved.** The sentence is gone from design.md (no match for it anywhere in the change except review.md). D6 ends with round 2's text, which restarts a wait only for "the set watch must rely on (main's, or the head's after a yes)", so before a yes no head-only request text is posted. D2's "lists the drift and the missing reviewers and merges nothing" stands, and D6 no longer contradicts it.

### Suggestions

1. **The first ADDED requirement contradicts the drift requirement as written.** "The merge policy comes from main" says the agent merge SHALL take `pr.merge_method`, `pr.reviewers` and the other keys from the default branch, "never from the PR branch". "A policy difference needs the user" says a yes merges "with the head's method", and the reviewer requirement uses the head's set after a yes. Read literally, a test of the first requirement would fail the confirmed path. Add "except after the user confirmed a difference (see A policy difference needs the user)". **Re-check: resolved by Required Change 3.**
2. **Proposal Impact (line 36), "In user mode watch makes three extra GitHub reads per ready head and sends no merge request".** With main `user` and a head that turns on `agent`, a yes does send a merge request (proposal line 12, the MODIFIED "Merging is opt-in"). Append "without the user's yes to a difference". **Re-check: resolved by Required Change 4.**
3. **Drift with a head in `agent` mode whose head set is short of D6 has no defined continuation.** D2 says watch "lists the drift and the missing reviewers and merges nothing". D6 restarts a wait only for "the set watch must rely on (main's, or the head's after a yes)", and before the question there is no yes. So it is unclear whether watch stops with a ready report, or restarts the wait with the head's `reviewer_args` and asks once they report. Concrete case: a legitimate PR adds a new required reviewer, and watch was started from a checkout that predates that commit. Both readings fail closed, but the implementation and the skill-text test will pick one arbitrarily. Name the behaviour in D2 and add a scenario. **Second re-check: open again, non-blocking.** With the R1 sentence removed, the design is back to round 2's text: D2's reading (list the drift and the missing reviewers, report ready, merge nothing) is the stated behaviour. If the author later wants the head-set wait, it must not post head-only request text before a yes (see Moderate R1), and it needs a new review round; it is not part of this verdict.
