## Findings

### Critical (blocking)

None.

### Moderate

**M1. A store rollback after a failed Step 7 is always refused, because the free check counts the update's own swapped files as dirty. The store stays on the new version, and every other project's gate stays blocked.**
D5 "Recovery of the lock" says a rollback after the lock was released "repeats steps 1-2 against the store" and stops when the store is "no longer free". Step 1 defines free as "on its main, and `git status --porcelain` empty apart from this update's own staging paths". After a completed swap, the store always has other changes too:
- `openspec/schemas/specwright/` differs from HEAD (or is untracked on a first claim);
- `openspec/.specwright/STORE` is new or modified;
- Step 5 has merged `openspec/config.yaml`.

None of these is a staging path, and the install never commits them (D5; README Step 8 leaves them for the user). So `recover --rollback` in a store reaches step 1 and always takes the "keep the swapped state" branch. The state-diagram edge `swapped --> rolledBack: ... store still free` and the Failure row for Step 7 ("asks to roll back") cannot happen for `owner` or `claim`. The consequence is the one round 2 M1 asked to avoid: an owner whose Step 7 fails cannot go back. `STORE` already reads the new version, so every other project on the old minor is stopped by its gate (D6) until it updates. The owner's own gate stops too, because its `VERSION` was not stamped.
The scenario "Rollback after another project moved on" passes, but no scenario covers the normal case (store untouched since the swap), so evals would not catch this.

**M2. A kill between taking the store gate lock and the first rename leaves an update lock that nothing removes.**
`swap` takes the lock "before its first rename" (D5) and then runs steps 1-3 under it: the store checks, then a second collection and validation pass. Per the Resource Bounds row, that pass can take up to about a minute. A kill or a closed terminal in that window (a `trap` does not run on SIGKILL or a lost terminal) leaves:
- the lock, with `change: specwright-update ...`;
- a journal with no target `old-moved` or `swapped`.

On rerun, `recover` takes D3's first branch, "swap not started → discard the staging". Neither D3, D5 nor the spec requirement "An interrupted store swap is recovered from its own checkout" (which says the takeover is "to resume or roll back") says that discard releases the lock. Two outcomes follow, both permanent:
- The lock stays. The next `swap` fails `mkdir` on it. Its journal is new, so the token does not match, and `recover` "stops, naming the holder".
- Separately, the design never fixes the order of `mkdir`, the `owner` file write and the journal token write. If the kill lands after `mkdir` and before the token reaches the journal, the token never matches either.

Every other project's gate and roadmap lock step then sees `specwright-update`, says to rerun the update there, and (by this change) does not offer removal. Nothing in the design or the README tells the user how to clear it. The store is blocked for every project until someone deletes a directory under `.git` by hand.
The State & Ownership row "Store gate lock" still says "Never automatic. The user confirms it is stale (existing rule)", which contradicts D5's takeover and no-removal rules. The eval's kill points come from `mv`/`cp`/`rm` shims, so a kill at the journal write after `mkdir` would show this. The design should state the expected result before the eval is written.

**M3. Step 5's `config.yaml` merge does not depend on the store role or on the result of the busy check, so the update writes the store in exactly the cases the spec says it must not.**
D1 keeps the `config.yaml` merge (Step 5) in the prompt, and README Step 5 merges `<root>/openspec/config.yaml`, which is the store's file. D5 decides at `swap` time whether the store is written: never for `other`, and not for a busy store on the patch path. But neither D1 nor D5 tells the prompt to skip Step 5 in those cases, and `swap`'s JSON is not specified to report it. Read as written:
- Scenario "Another project updates within the store's version" requires the store's `config.yaml` to be byte-identical, and Step 5 rewrites its managed `context:` lines.
- Scenario "Store busy, schema unchanged" requires "the store's files ... unchanged". Step 5 then writes `config.yaml` into the working tree of the store's change branch (`feat/add-x`). That change's commits leave the file dirty, and the next gate stops on it.
- If Step 5 is skipped there, Step 7 still checks that `<root>/openspec/config.yaml` has "every downloaded context line exactly once". For `other` on a patch whose context lines differ from the owner's, that check fails, so `VERSION` is never stamped and the journal stays `swapped`.
- For the owner, Step 5 runs after `swap` released the lock and is not in the journal, so a rollback (once M1 is fixed) restores the schema and `STORE` but leaves the new version's managed context lines.

### Suggestions

- **S1. Two claims at once: the scenario's THEN does not follow from D5's order.** In "Two projects claim at once", B's swap "finding that record under the lock, stops ... and names owner A". D5 runs step 1 (free check) before step 2 (re-read `STORE`). On one machine, A's uncommitted `STORE` and schema make the store dirty, so B stops at step 1 and names dirty paths, not owner A. Either run step 2 before step 1, or change the THEN to "stops before any write and names `openspec/.specwright/STORE` among the dirty paths". As written, the eval for that scenario fails against a faithful implementation.
- **S2. Branch attribution serves only an off-workflow state.** A change in progress keeps the store on its branch from gate to archive (`specwright-branch` store step 2; `specwright-finish` archives on the branch). After the archive commit, the branch tree no longer holds `<P>/changes/<name>/`. A store on main with an unarchived change on a local store branch therefore exists only when a change was abandoned and the store was switched back by hand. The Mechanism Ledger's reason ("Without it every in-flight store change blocks the owner, even their own") is already covered by the free check, which blocks every change actually in progress. A simpler rule (any unarchived local store branch blocks a store workflow swap, naming the branch and the remedy, finish or delete it) would drop the code-repo branch lookup and its known misattribution risk. Keep attribution only if there is a reachable case it serves.
- **S3. Stale proposal text.**
  - What Changes still says "Patch updates always proceed" (line 25), but line 27 and the planning-stores requirement refuse an owner's patch with a changed schema on a busy store.
  - Impact still calls `STORE` "recoverable working state under ADR 0003" (line 55), which the design's ADR section now records as a departure from 0003 (round 2 S4).
  - Impact lists only `skills/specwright-branch/SKILL.md`, but the requirement "An interrupted store swap is recovered from its own checkout" also changes the lock step in `skills/specwright-roadmap/SKILL.md` (line 33), so tasks derived from the proposal could miss it.

## Verdict

VERDICT: APPROVE_WITH_CHANGES

## Required Changes

1. **(M1)** In design D5, step 1, define "free" for a rollback or resume run by `recover` as: on its main, and `git status --porcelain` lists nothing beyond this update's staging paths and the store paths the journal records as written by this update (the schema target, `STORE`, and `config.yaml` once change 3 records it), each still matching the content the journal recorded for the swapped state. Any other path, or a different branch, is busy. Add a planning-stores scenario under "An interrupted store swap is recovered from its own checkout": "Rollback after Step 7 failed, store untouched since" (WHEN A's swap completed and released the lock, Step 7 failed, and the store is on main with only A's swapped schema, `STORE` and merged `config.yaml` uncommitted; THEN the rollback takes the lock, restores the previous schema, `config.yaml` and `STORE` record (or removes `STORE` after a claim), releases the lock and reports `rolled back to <previous>`).
2. **(M2)** In design D5, state the order: `swap` writes the token into the journal (atomic write) before `mkdir` of the gate lock, then writes the `owner` file. In D3 and D5, state that `recover` releases a gate lock whose `owner` names `specwright-update`, this checkout and the journal's token in every outcome (discard, resume, rollback, finish-only), and a lock whose `owner` file is missing or empty is shown to the user under the existing confirm-then-remove rule. In the planning-stores requirement "An interrupted store swap is recovered from its own checkout", change "to resume or roll back" to "to discard, resume or roll back", and add the scenario "Interrupted after taking the lock, before the first rename" (THEN the rerun discards the staging, removes the lock, reports `discarded unfinished update to <to>`, and no lock is left). Replace the State & Ownership row "Store gate lock" invalidation text with: "Gate and roadmap locks: never automatic, the user confirms it is stale. The update's lock: taken over and released only by `recover` from the same checkout with the journal's token (D5)."
3. **(M3)** In design D1 and D5, specify that `swap`'s JSON reports whether it wrote the store (`store_written: true|false`). The prompt then runs Step 5 on `<root>/openspec/config.yaml` only for role `none`, or when `store_written` is true. Otherwise it skips Step 5, and in Step 7 reports the `config.yaml` check as "store config managed by owner <id>" instead of failing it. For `owner` or `claim`, `swap` saves the store's previous `config.yaml` in the schema staging directory and records it in the journal, so that rollback restores it. Add to the planning-stores scenario "Store busy, schema unchanged", and to "Another project updates within the store's version", that `VERSION` is stamped.
