## Findings

### Critical (blocking)

**C1. The archive-only carry-over lets an agent merge a head no reviewer saw.** In agent mode watch archives without asking, and when `archive-only` reports `archive_only: true`, watch watches the archive head "without `--reviewer` arguments: readiness needs CI, mergeability and no new feedback" (`skills/specwright-pr/SKILL.md:134`). Nothing then binds readiness to the archive head: `readiness()` (`pr-pair.sh:1141-1170`) checks state, mergeability, checks, items and the reviewers it was given, never that `head_oid` is still the archive head. If any commit lands on the branch after the archive push (another session of the user, a collaborator, a bot), the reviewer-less watch sees CI green and no feedback on that new head, reports it ready, and the merge's head guard then passes, because the guard is the *ready* head (D2), not the head reviewers reported on. The result is an irreversible merge of an unreviewed commit to the default branch, the exact outcome the design claims is excluded ("nothing unreviewed is merged", Flow & State Gaps; Mechanism Ledger row 1). In `pr.merge: user` this gap is harmless because a person merges; agent mode makes it a merge. The head guard as designed protects only the ready → merge window, not the archive push → ready window.

### Moderate

**M1. With the shipped template, agent-mode readiness has no review condition at all.** Readiness requires reviewers only through the `--reviewer` entries built from `pr.reviewers` (`SKILL.md:44`, `pr-pair.sh:1164-1168`). The template ships `pr.reviewers` commented out (`templates/openspec/specwright.yaml:82-83`), so a project that only sets `pr.merge: agent` watches with no reviewer at all: ready means CI green, no comments and one quiet wait. A review requested by `review_request.body` that arrives after that quiet wait (a slow or down Codex) is never waited for, and the PR is merged unreviewed. The design's Context and Risks lean on "every required reviewer reported" and "watch's existing readiness check", but for the default reviewer configuration that clause is empty. This repo's own config sets reviewers (`openspec/specwright.yaml:83`), which is why dogfooding here would not show it; a new opted-in project would.

**M2. Store-backed failure after the store merged is described as recoverable by watch, but `pair-state` stops every later watch.** Once the store PR is MERGED and the code PR is OPEN, `cmd_pair_state` returns `split_hand_off` (`pr-pair.sh:1222-1224`), and watch stops "archiving and re-requesting nothing" (`SKILL.md:125`). The design contradicts this in three places: the Failure table's store-backed row says retry is safe "by the user or a later watch"; the state diagram sends `refused head_changed` back to `Waiting` with no store-backed exception; and the spec's "Head moved after ready" scenario says watch "watches `def456` instead", while the store-backed requirement says a refused second merge stops. An implementer following the diagram for a code-side `head_changed` would restart a wait that the next `pair-state` call immediately turns into `split_hand_off`, and the user is told a later watch will finish the job when it cannot. The recovery path (the user merges the code PR, then "the PRs merged" or finish's **After the PR is merged** cleans up) needs to be the one stated.

### Suggestions

**S1. Finish's hand-off requirement drops the existing "watch started this archive" branch.** `specwright-finish/SKILL.md:80` hands back to watch when watch started the archive. The new requirement says that in agent mode finish "SHALL continue in watch" after shipping, unconditionally; in the auto-archive path (which agent mode always takes from watch) that reads as starting a second watch on the same PR. Ownership claims make the older wait exit 4, so this is not unsafe, but the requirement should keep "hand back to watch when watch started the archive; otherwise start watch" and the spec could add that scenario.

**S2. The resume path through finish does not reach `delete-remote` as written.** D6 relies on finish's **After the PR is merged** running "the same cleanup, remote deletion included", but in repo-local mode that section runs its own checkout/pull/branch-check commands and only defers to Cleanup after merge for `closed-check` (`specwright-finish/SKILL.md:81`). Name that section in the tasks and add a spec scenario (agent mode, session died after merge, user says "merged", the remote branch is deleted under the same SHA and base checks).

**S3. Validate `pr.merge_method` (and `pr.delete_branch`) when watch starts, not when the PR becomes ready.** The "Invalid method" scenario only says "stops before any merge request"; reporting it after hours of watching wastes the whole wait. An unrecognised `pr.delete_branch` value is also unspecified (treat as `false` and report, mirroring `pr.merge`).

**S4. Store-backed with no store PR expected (`share_store_by_hand`, `pr-pair.sh:1213`).** The code PR alone is the expected set, so agent mode merges it while the archive sits on an unshared store branch; roadmap status then cannot see the change as done. The behaviour is acceptable, but the merge report should repeat the share-by-hand reminder, and a spec scenario would pin it.

## Verdict

VERDICT: APPROVE_WITH_CHANGES

## Required Changes

1. **C1 (design D2/D4, Flow & State Gaps, spec "Only the ready head is merged").** In agent mode, after a watch of the archive head without reviewers, merge only when the ready head equals the archive head that `review-run.sh archive-only` judged. If the PR head is any other commit, run `archive-only --base <ready head before the archive> --head <current head>` again; unless it still reports `archive_only: true`, return to watching with the reviewers (re-requesting review per the existing rules), or report ready and stop without merging. Add a spec scenario under "Only the ready head is merged": WHEN `pr.merge` is `agent`, the archive head was watched without reviewers, and a commit `def456` lands on the branch after the archive push, THEN no merge request is sent for `def456` until required reviewers have reported on it. Correct the Flow & State Gaps bullet and Mechanism Ledger row so they no longer claim the head guard alone prevents unreviewed merges.
2. **M1 (spec "Merging is opt-in", design Context/Risks, template and README items).** Decide and specify readiness without required reviewers. Recommended: agent mode merges a PR only when its repository's reviewer set (`pr.reviewers`, store: `planning_store.reviewers`) has at least one `required` entry; otherwise watch reports ready, states `agent merge needs a required reviewer in pr.reviewers`, and merges nothing; add a scenario for it. If instead the author accepts merging without any required reviewer, record that as an explicit decision in design.md (with the consequence: a review requested only through `review_request.body` may arrive after the merge) and in ADR 0009's contract, and add a spec scenario that fixes the behaviour.
3. **M2 (design Failure table, state diagram, spec).** State that after the store PR merged, any code-merge outcome other than `merged` (refused, `head_changed`, unknown) stops with `planning merged, code pending`, and that a later watch also stops (`pair-state` `split_hand_off`); recovery is the user merging the code PR, then Cleanup after merge. Fix the Failure table row ("by the user, then cleanup"; not "a later watch"), add the store-backed exception to the `Merging --> Waiting: refused head_changed` transition, extend the "Code merge refused" scenario to cover a changed code head, and scope the "Head moved after ready" scenario to a repo-local PR (or a store-backed pair before any merge).
