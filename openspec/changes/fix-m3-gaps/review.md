## Findings

### Critical (blocking)

None.

### Moderate

**M1. D3's "the branch bumped" test is defeated by merging main into the branch, which reopens #94.**
D3 and the `releases` delta define "bumped" as "the working-tree version differs from the version at `git merge-base HEAD <ref>`". Merging main into the change branch moves the merge base to main's tip. Take the issue's own timeline: `feat/a` and `feat/b` both bump 0.4.2 to 0.5.0, and `feat/a` merges. Then `feat/b` is brought up to date, either with GitHub's "Update branch" button (a merge of main into the head, which a "require branches to be up to date" rule asks for) or with `git merge main` to resolve a conflict before a local finish. The identical `VERSION` edits merge cleanly. Now `merge-base(HEAD, origin/main)` is main's tip, which reads 0.5.0, and the working tree also reads 0.5.0. `check --main` classifies the branch as "did not bump" (the delta scenario "Branch did not bump") and exits 0 at ship, local merge and watch. `feat/b` merges with no version of its own. `untagged` lists nothing because `v0.5.0` is already tagged, and the change is never released under its own version. That is exactly the harm in #94. Specwright itself never rebases or merges main into the branch (`specwright-pr` Never), but the user and GitHub can, and D3 states that it guards the user-merge path too.

**M2. On the subagent route, a refused design review still overwrites the earlier `review.md`, against the new spec text and the design's State table.**
The MODIFIED `review-routes` requirement now says that a route whose output fails validation, "the subagent included", SHALL "leave any earlier review file unchanged". The design's State & Ownership row for `review.md` says "A failed run never writes it". For the subagent route, though, the `specwright-reviewer` agent writes `review.md` itself (`schema.yaml:317-320`, `specwright-review/SKILL.md:43`). Only afterwards does `record` validate the file in place (`review-run.sh:1064-1069`), and on refusal it does not restore anything. So a subagent that returns `VERDICT: BLOCKED`, which is the #95 case, has already destroyed the previous review by the time D5 refuses it. That is the data loss D5's rejected alternative cites. The change directory is untracked while the change is planned (`?? openspec/changes/fix-m3-gaps/` in this checkout), so `git restore` cannot recover the earlier file, unlike the issue's case. A refused `VERDICT: USER_OVERRIDE` from a subagent also stays on disk, and the tasks PRECHECK (`schema.yaml:375-379`) accepts that value. Specwright would then start tasks on a review that `record` rejected, unless the orchestrator obeys the exit 3.

**M3. D8 cannot tell "the change fails on the installed schema" from "the installed schema fails under the current OpenSpec", so it can blame the change wrongly.**
`check_change` (`update.sh:1155-1188`) returns one error string for any of its three steps. The first step is `openspec schema validate specwright`, which checks the schema, not the change. D8 appends "it already fails on `<installed>` (`<that error>`), so the update to `<to>` did not cause it" whenever the installed-schema recheck returns an error. An older installed schema can fail `schema validate` under the OpenSpec version the install now pins: the update runs with the new pin, 1.14.1, and the installed schema was checked against whatever pin it shipped with. In that case the message says the change is already broken on the installed version, when the change may be valid there. That is the mirror image of #99's misattribution. The Failure & Visibility row "`openspec` fails on the installed schema → the message keeps only the target error and makes no claim" states the intended behaviour, but no mechanism produces it. The ADDED requirement also has no scenario for this failure path.

### Suggestions

- **S1 (D3, first release-enabled branch).** D3 does not say what `check --main` does when the primary file, or a version match, is missing at the merge base or at `<ref>`. An example is the change that first adds `VERSION` together with `release.enabled`. Today that path would reach `sv(None)` or an `internal_error` at ship. Suggest: no readable version at `<ref>` → nothing to collide with, exit 0. Add a scenario.
- **S2 (D2, JSON field).** `"tags": "origin"` for the default `untagged` output is false when there is no `origin` remote, because `published_tags` then reads local tags (`release.sh:735-737`). Report `"tags": "local"` in that case too, so finish's "the list comes from local tags" wording stays truthful.
- **S3 (D6, bound headroom).** `agent_end` carries the whole message list (`omp_last_text` filters `end["messages"]`), tool results included. Its line therefore grows with how much the reviewer reads, which is the growth that broke `MAX_OUTPUT` in #95. `MAX_EVENT_LINE` = 16 MiB is roughly 12x the 1.35 MB session in the issue. The Resource Bounds row should say that a 100x review hits `output too large` again with a small answer, or name what would raise the bound. Also read with `readline(MAX_EVENT_LINE + 1)`, so that the memory bound holds before a line is measured.
- **S4 (D5/ADR 0007).** ADR 0007's Decision text still describes design validation as "exactly one `VERDICT:` line and a `CHANGES_APPLIED:` line". The design updates only the architecture Contracts sentence. Consider a one-line note in the ADR's Consequences, or name the tightening in the architecture row, so that the ADR does not read as the full contract.
- **S5 (D9, stash ref drift).** `stash@{n}` refs shift when any later stash is pushed, so a ref reported in one run can name another stash in the next. The start-of-run scan already matches by message. State that restore and drop always re-resolve the ref by message just before `apply`/`drop`, never from the earlier report.

## Required Changes

1. **M1, `design.md` D3 and `specs/releases/spec.md`.** Redefine "the branch bumped". It bumped when the working-tree version differs from the merge-base version, **or** when a non-merge commit in `<ref>..HEAD` changes the primary version file (`git log --no-merges --format=%H <ref>..HEAD -- <primary spec>` is non-empty). Update the ADDED requirement's text to match. Add a scenario: "**WHEN** `feat/a` and `feat/b` both bumped 0.4.2 → 0.5.0, `feat/a` merged, and `origin/main` was then merged into `feat/b` / **THEN** `check --main origin/main` exits non-zero naming 0.5.0 on both and says to bump again". Keep "Branch did not bump" for a branch with no such commit.
2. **M2, `design.md` D5 and State table, `specs/review-routes/spec.md`.** Choose one option and state it.
   - (a) The subagent writes its design review to a scratch result file, and `record --kind design --out <review.md>` writes `review.md` atomically only when it validates. This needs edits to the schema review instruction, `specwright-review` Design reviews and the `specwright-reviewer` agent text, added to the Impact list, and a scenario: "subagent returns `VERDICT: BLOCKED` while `review.md` holds an earlier valid review → `record` exits 3 and `review.md` is byte-identical".
   - (b) Scope the "leaves any earlier review file unchanged" clause to CLI routes, correct the State-table row, and add a scenario in which a refused subagent result is not used by the tasks step.

   Option (a) is preferred, because an untracked change directory cannot be restored from git.
3. **M3, `design.md` D8 and `specs/install-update/spec.md`.** Make the installed-schema claim depend on which step failed. `check_change` (or a variant) reports the failing step. The "already fails on `<installed>`" sentence is appended only when the installed schema passes `openspec schema validate` and the change fails `validate <name>` or `status <name>` against it. When the installed schema itself fails `schema validate`, or `openspec` errors, the message keeps only the target error. Add the matching scenario to the ADDED requirement: "installed schema fails `openspec schema validate` → the refusal names `add-x` and the target error and makes no claim about the installed version".
