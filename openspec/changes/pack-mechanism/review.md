### Moderate

**M1. Step 5 and pack-verify need the previous `packs.json`, but by the time they run the swap has already replaced it, and the design never says where they read it.** (Ownership, Failure)
Since the round-2 fix, the line merge and the `not_enabled` check depend on "enabled in the previous `packs.json`" (D5; install-update requirement "Pack lines are merged by prefix and verified through OpenSpec"). D4 and the "records" requirement put `packs.json` in the swap, and Step 5 and pack-verify run after the swap (sequence diagram; README Step 5 follows Step 4's swap). When they run, the record on disk is the new one. The previous record exists only as the `old/` copy in the staging directory, and only until `finish`. No requirement or decision says that Step 5 or pack-verify reads that copy, or that plan or the journal carries the previous enabled set.

This has a concrete consequence on a path the design documents. Flow & State Gaps says "Swapped but Step 5 not run: ... a rerun goes straight to Steps 5-7 (the existing `swapped` path)". README Step 4 confirms that this rerun skips `stage` and `swap` in a new session. That session can read only the new `packs.json`. Take a user who removed `web` from `packs:`. `web` is now neither enabled nor in the record that session can see, so Step 5 keeps every `[pack:web] ` line as "not managed". pack-verify, with the same view, finds no line of a "pack enabled before", passes, and `VERSION` is stamped. The removed pack's rules keep reaching OpenSpec. On every later install they look hand-written, so no update ever removes them. That breaks the requirement "A pack that is no longer enabled is removed" ("`config.yaml` has no `[pack:web] ` line"). An agent that simply reads `packs.json` at Step 5 in the normal, uninterrupted path hits the same failure.

Fix: make the previous enabled set part of the journal. `stage` records the installed record's enabled pack names in journal format 2 (for example `prev_packs`). `plan` reports them as `packs_previous`, from the installed record on a fresh run and from the journal on a resumed `swapped` run. Step 5 uses `plan`'s `packs_previous`, and `pack-verify` reads the journal (which exists until `finish`, after the stamp). Add a scenario: "the swap that removes `web` finished and the run stopped before Step 5; the rerun's Step 5 removes the `[pack:web] ` lines and pack-verify would report a kept one as `not_enabled`".

**M2. The Flow & State Gaps and Risks entries still use the catalogue rule that round 2's M1 replaced.** (Decisions: contradiction)
Flow & State Gaps says: "A user edits a `[pack:` line by hand: for a catalogued pack the next install removes and re-adds it (README: pack lines are managed); for an uncatalogued name it is kept and reported." D5 and the spec now key this on enabled now or enabled before, not on being in the catalogue. A hand-edited line of a catalogued pack that was never enabled is kept. That entry also tells the implementer what the README will say. A README Step 5 or "pack lines are managed" note written from it would tell Tower of Lament users the wrong thing, and an agent following it would bring back the silent deletion that round 2's M1 removed. The Risks entry gives "(not catalogued)" as the reason the lines are kept until `gamedev` ships. That is the old reason, and the entry does not say the lines are also kept after 0.16.0 until the project enables the pack. Round 2 required "Reword the Risks entry for Tower of Lament to match".

**M3. D4's orphan rule for unrecorded skills contradicts the install-update spec.** (Decisions: contradiction; T6) D4 lists "a skill directory named like a catalogued, not enabled pack's skill with no record" as an orphan. The install-update requirement "The install never touches a skill it did not install" lists only recorded pack skills that the download no longer ships. README Step 4 has the agent "ask before removing" every orphan. Under D4's rule, from 0.16.0 every update of Tower of Lament without `gamedev` enabled would offer to delete its hand-copied `gamedev-*` skills, while its hand-written `[pack:gamedev]` lines are kept as not managed. Fix: align D4 with the spec. Only recorded pack skills that the download no longer ships are orphans. An unrecorded hand copy of a catalogued, not enabled pack's skill is neither listed nor touched, the same as a user's unrelated skill.

## Required Changes

1. M1: In design.md D5 (and D3 or D4, wherever the journal format 2 fields are listed) and in specs/install-update/spec.md, state where Step 5 and `pack-verify` read the previous enabled pack set after the swap has replaced `packs.json`. Suggested wording: `stage` records the installed record's enabled pack names in the journal (`prev_packs`). `plan` reports them as `packs_previous`, taken from the installed `packs.json` on a fresh run and from the journal on a resumed `swapped` run. Step 5 uses `packs_previous`, and `pack-verify` reads `prev_packs` from the journal. Add a scenario to the requirement "Pack lines are merged by prefix and verified through OpenSpec": "**WHEN** the swap that removed `web` from `packs:` finished and the run stopped before Step 5, and the prompt is rerun **THEN** Step 5 removes every `[pack:web] ` line, and pack-verify reports any line left as `not_enabled`". Update the "Swapped but Step 5 not run" entry in Flow & State Gaps to match. **Checked: applied.** D5 now opens with the source: `stage` writes the record's enabled packs into journal format 2 as `prev_packs` before the swap, and `plan` reports `packs_previous` (from a pending journal, else from `packs.json`). Step 5 and `pack-verify` (`--previous <name>`, taken from plan's value) use only that, never the swapped `packs.json`. The new install-update requirement "The previously enabled packs come from the start of the update" states the same, with scenarios for an uninterrupted removal and for no previous record. The merge requirement is keyed on `packs_previous`. The scenario "A removed pack's lines after a rerun past the swap" matches the one this item asked for. Flow & State Gaps "Swapped but Step 5 not run" says plan takes `packs_previous` from the pending journal's `prev_packs`. Passing the set to pack-verify as `--previous` from plan, rather than having pack-verify read the journal itself, is equivalent: on the rerun path plan reads it from the journal.
2. M2: In design.md Flow & State Gaps, change the entry "A user edits a `[pack:` line by hand" to key on "a pack enabled now or in the previous record" instead of "catalogued", and on "any other pack" instead of "an uncatalogued name". In Risks, replace "(not catalogued)" with the actual rule: the lines are kept until the project enables `gamedev`, before and after 0.16.0. **Checked: applied.** Flow & State Gaps "A user edits a `[pack:` line by hand" now keys on "a pack enabled now or before (`packs_previous`)" and "any other name". The Risks entry for Tower of Lament now says the lines are kept until the project enables `gamedev`, "whether or not `gamedev` ships in the download" (never enabled, so not managed).
3. M3: In design.md D4, align the orphan rule with specs/install-update/spec.md, requirement "The install never touches a skill it did not install". Only a recorded pack skill whose name the download no longer ships is listed in `orphans`. A skill directory named like a skill of a catalogued, not enabled pack, with no record, is neither listed as an orphan nor changed. Add a scenario to that requirement: "**WHEN** `.claude/skills/gamedev-design/` was copied by hand, the download catalogues `gamedev`, the project does not enable it and no record lists it **THEN** plan does not list it in `orphans` and the install leaves it unchanged". **Checked: applied.** D4 now says that orphans are only recorded pack skills the download no longer ships, and that an unrecorded skill directory of a pack that is not enabled is neither listed nor touched. The install-update spec has the scenario "A hand copy of a pack that is not enabled" (not in `orphans`, left unchanged), matching the requirement text.
