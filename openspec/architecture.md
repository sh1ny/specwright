# Specwright Architecture

Specwright is not a running service. It is text and small scripts that an AI agent loads and follows inside a user's project. "Components" below are therefore instruction packages, scripts and the external tools they drive. The agent is the only process that runs them.

## System triage

- **T1 Components:** applies. There are eight skills, two agents, a schema, four PR scripts, the review runner, the release script and an install prompt, with directed calls between them (see Components).
- **T2 State:** applies. Change artifacts, `tasks.md` ticks, commit trailers, PR reply markers, the feedback pass record, pre-ship review records and the store gate lock are all persistent state.
- **T3 Concurrency:** applies. Several agents share one machine, one `gh` login store and one planning store. `watch` polls in the background, reviewers answer asynchronously, and a review runs as a background job under a deadline.
- **T4 Boundaries:** applies. The schema is OpenSpec's extension point; `specwright.yaml` is a shared, versioned settings format; commit subjects, trailers and PR markers are formats that later runs parse; GitHub and the model CLIs are external systems.
- **T5 Volume:** applies. PR threads, comments and checks grow without a fixed bound, and so does commit history per change.
- **T6 Risk:** applies. The scripts push and comment under a GitHub identity, and cross-model review sends code to another provider.

## Boundaries and contracts

- **OpenSpec:** only through the custom schema and the CLI (`list`, `show`, `new change`, `instructions`, `templates`, `schema validate`, `validate`, `archive`, `context --json`). The OpenSpec version is pinned in `OPENSPEC_VERSION` (mirrored by the README badge, the public install commands and `CONTRIBUTING.md`, kept in step by `TestOpenSpecPin`) and enforced at install: the install prompt requires an exact match with `openspec --version` before it writes anything, except through an explicit, per-run override the user states.
- **Settings:** `specwright.yaml` keys are documented in `templates/openspec/specwright.yaml` and the README. A new key has a safe default, so a missing key keeps earlier behaviour.
- **Git evidence formats:** commit subjects `<type>(<change>): task X.Y …` and `<type>(<change>): address pre-ship review`, trailers `Feedback-Round:`, `Preship-Round:`, `Amendment:` and `Code-Changes: none`, the legacy `address review feedback` subject (counted as a round only on a branch with no trailers in either repo), archive/merge subjects, and the planning-only marker. Later runs and roadmap status parse these, so changing them is a workflow change (minor version).
- **Commits** (ADR 0016): `commit_granularity` (`task` default, or `group`) in `specwright.yaml`, the `<type>(<change>): group N <heading>` subject and the `Specwright-Task: X.Y` trailer are parsed by later runs (`task-cover.sh`, Reconcile, the end-of-apply check), so changing them is a workflow change (minor version). A task is covered by a subject starting `<type>(<change>): task X.Y ` or an exact `Specwright-Task` trailer value read by Git's trailer parser.
- **Releases** (ADR 0010): `release:` settings in `specwright.yaml` (`enabled` default false, `version_files` as a path → regex map whose first key is the primary file, `tag` default `v{version}`, `github_release`, `auto`) and the tag name and annotation format are parsed by later runs (the previous-release lookup), so changing them is a workflow change (minor version). The same holds for the `## Release Notes` section of `proposal.md` (summary, then `### Added`/`Changed`/`Fixed`/`Removed` lists; ADR 0015), which later runs parse from the archive. The release commit of V is the first commit in main's first-parent history whose primary version file reads V; `release.enabled` with `pr.merge_method: rebase` is refused. A tag is created once and never moved, deleted or force-pushed, and only the code repo is tagged.
- **Install and update** (ADR 0011): the install prompt downloads the highest release tag and drives `scripts/update.sh` through its `interface` (an integer; another value stops before staging). The journal (`format: 1`) and `STORE` (`version:` and `owner:`, the owner being the code repo's `origin` as `host/owner/repo`) are formats later runs parse, so changing them is a workflow change (minor version). `specwright-branch` compares `major.minor` of `VERSION` and `STORE.version` at the gate and stops on a mismatch.
- **VCS backend selection** (ADR 0018): `vcs` selects the code repository's version-control backend (`git`, `jj` or `gitbutler`) and `planning_store.vcs` independently selects the planning store's backend (`git` or `jj`); each defaults to `git`, and `gitbutler` needs `finish: pr`. Later runs parse these settings through `pr-pair.sh vcs`; neither setting is inferred from repository contents, and the store does not inherit the code setting.
- **Script I/O** (ADR 0002): `pr-snapshot.sh` and `pr-pair.sh` print one JSON document (`pr-snapshot.sh --logs` appends plain log text); `pr-reply.sh` prints one plain line per action. Exit codes signal stop conditions. `pr-pair.sh item-issues --repo o/n --item <id>...` prints `{"ok":true,"found":{"<id>":N},"missing":["<id>"]}`. A network limit (ADR 0012) is named `deadline_exceeded` or `response_too_large`: the `error` of `pr-pair.sh`'s JSON (exit 3, unknown), `as.sh: <limit>: <command>` (exit 3), or `bounded: <limit>: <command>` on stderr in `pr-snapshot.sh` and `pr-reply.sh`. Scripts use only `bash` with a POSIX userland (`sed`, `grep`, `mktemp` and similar; Git Bash on Windows), `git`, `gh` 2.40+ (built-in jq) and the Python standard library (all four PR scripts, `as.sh` included, need 3.8+ and exit 2 without it; `pr-pair.sh` accepts 3.8+, but `pass write` needs 3.10+ and fails with a traceback, not JSON, on older versions: #46); `pr-pair.sh` runs `git` in the code repo and the store for repo identity, the expected PR set, recovery and cleanup.
- **GitHub identity** (ADR 0008): every `gh` call and every git network call to a github.com remote runs through `as.sh <run login>` (or, for `pr-pair.sh`'s own `gh` calls, its internal fence that resolves and verifies the token the same way), and `gh auth switch` is never run. The run login is the configured login (`github.login`, `planning_store.login` for the store); with none, the first user-started step of a run resolves the active account once with `as.sh --resolve` and hands the login to every step it invokes, so a later switch cannot redirect the run; empty fallbacks (`review_request.login`, `pr.request_as`) end at the run login. `git fetch` and `git pull` on main are fenced when the remote's fetch URL is on github.com, and plain for other hosts; in the branch gate and roadmap status a refusal (including a failed `--resolve`) means local refs only, elsewhere it stops. `pr-pair.sh` runs every network read of a repository other than the one it started in through `as.sh <that repo's login>` from inside it, and `cleanup-plan` emits fenced pulls. On a jj repository, `vcs.sh` routes jj fetch and push through `as.sh`; these commands have no added deadline and remain outside ADR 0014's scope. `as.sh` refuses (exit 3) when a github.com URL git could use, a github.com rewrite rule, a URL argument or a `-c` value carries userinfo, and unsets `GH_HOST` and the enterprise token variables.
- **Reviewer routes** (ADR 0007): `review-run.sh select` walks `review.order` (default `[codex, claude, omp]`), skips the current harness and takes the first installed route whose probe passes, else the `specwright-reviewer` subagent; `review.cross_model: false` means the subagent only. Each route runs one fixed command line from the script with read-only tools by allowlist, the user's skills, extensions, rules and slash commands off, and a fresh OMP session dir; the prompt goes by file. For a pre-ship review the script embeds the code-range diff (and the store-range diff) in a nonce-delimited untrusted region, bounded by `review.max_diff_kb`. Output is validated, fail closed, from every route including the subagent: pre-ship findings against `findings.schema.json`, design reviews as a review file with exactly one `VERDICT:` line whose value is `APPROVE`, `APPROVE_WITH_CHANGES` or `REVISE`, and exactly one `CHANGES_APPLIED:` line that fits it (`no` or `yes` after `APPROVE_WITH_CHANGES`, else `n/a`); this tightens ADR 0007's validation. The subagent writes a design review to a scratch file from `record --scratch`, and `record --out` copies it to the review file only when it validates, so a refused review never replaces an earlier one. For OMP the 2 MiB bound applies to the answer in the last `agent_end` event, not to the event stream. On Windows the codex route passes on only the user's `windows.sandbox` setting. A failed review exits 3 and never falls through to another route. Every run writes a receipt (route, skipped routes with reasons, requested and actual model and level). The diff and the files the reviewer reads go to that route's provider.
