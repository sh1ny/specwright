# Specwright Roadmap

Strategy: [openspec/strategy.md](strategy.md) · Architecture: [openspec/architecture.md](architecture.md)

Specwright already exists (0.1.8), so M1 is not a walking skeleton: it closes the gaps between the code and the architecture baseline that most often force a manual rescue. Issue numbers refer to sh1ny/specwright. Versions follow the pre-1.0 rule in [strategy.md](strategy.md#assumptions): one minor version per feature, configuration key or workflow change, and a patch version per fix.

## Now: M5 - Commits and VCS backends

**Outcome:** commits are shaped by the work, not by the tool. A project can commit once per task group instead of once per task, and can run the whole workflow on jj or GitButler instead of plain Git, with Git staying the default. The gaps found during M4 are closed first, including the codex review route on Windows, and release notes say what each release shipped from then on.

**Exit criteria:**
- Every issue in the changes below is closed by a merged PR, and each code fix has a regression test in `evals/`. (agent)
- `evals/pr-pair`, `evals/git-workflow`, `evals/review-routes`, `evals/update`, `evals/release` and `evals/finish` pass. (agent)
- An eval with a hung or oversized response shows `release.sh`, `finish.sh` and `update.sh` stopping within their deadline or bound with a named error. (agent)
- The codex route completes a design review on Windows, recorded as a trial in `evals/review-routes/trial.md`, and a failing codex run reports codex's own error from its event stream. (agent)
- With `commit_granularity: group`, an apply of groups `1.1`-`1.3` and `2.1`-`2.2` makes exactly two task-work commits whose `Specwright-Task:` trailers cover all five tasks; group 1 never takes a group 10 task; a resume after an interrupted group, and after either half of a code/store pair, makes no duplicate and loses no tick. With it unset, per-task commits are unchanged. (agent)
- With `vcs: jj`, branch, apply, archive and finish run on a colocated repo in `local` and `pr` modes with every write made through jj; with `vcs: gitbutler`, commits go to the change's own branch, other workspace changes stay untouched and only the change's PR is opened. A missing tool or a repo the backend does not manage stops before any write, and with `vcs` unset the Git flow is unchanged. (agent)
- Each eval suite's wall time on Windows is measured before and after `fix-eval-gaps`, and the total is lower. (agent)
- A change runs only the eval suites its changed paths map to, and a GitHub Actions workflow runs every eval suite on Linux for each pull request and passes on the PR that adds it. (agent)
- The notes `release.sh` writes for a release whose changes have Release Notes sections open with the release summary, then list every item under its `Added`, `Changed`, `Fixed` or `Removed` heading with its issue or PR reference; a change without the section falls back to its Why line under `Changes`. (agent)
- Each change ships as its own release: 0.8.1, 0.9.0, 0.9.1, 0.9.2, 0.9.3, 0.10.0, 0.11.0 and 0.12.0. (agent)

**Changes** (in order; each about one PR):
1. `fix-m4-gaps` (0.8.1) - known gaps filed during M4: #111 network commands in `release.sh`, `finish.sh` and `update.sh` bounded like the PR scripts (ADR 0012); #113 codex's answer file capped while it is written; #114 an exit in the last poll interval with a held pipe is not a timeout; #116 a Windows descendant holding the capture pipes is stopped; #117 a fractional `SPECWRIGHT_NET_DEADLINE` applies to the poll-wide deadline; #115 a code span between the keyword and the reference breaks a closing reference; #110 `after_rerun` never recreates a main spec deleted after a bulk archive; #109 a revert between two unreadable versions no longer counts the older bump.
2. `sectioned-release-notes` (0.9.0) - #130 release notes say what shipped instead of why: a `## Release Notes` section in `proposal.md` (a one- or two-sentence summary, then `Added`, `Changed`, `Fixed`, `Removed` items, each with its issue or PR reference), written with the proposal, kept current during apply and checked against the diff in the pre-ship review. `release.sh` merges the sections of every change in the release and adds the change's PR to items without a reference; the release summary is written by the version-bump task, so the tag message stays rebuildable from the repo. Changes archived without the section fall back to today's Why line.
3. `fix-eval-gaps` (0.9.1) - eval grader, fake `gh` and eval speed gaps filed during M4: #119 a GraphQL mutation sent with `-X GET` is a write; #121 `git fetch` with no refspec is a write (it follows tags); #122 `git branch -q --list` and #123 `git tag -v` are reads; #124 `graphql_read_only` honours `operationName`; #125 the fake `gh` dispatches only the named operation; #127 fewer process launches per test (fixture repos built once and copied, the fake `gh` in-process where no process boundary is needed), with each suite's wall time measured before and after.
4. `targeted-eval-runs` (0.9.2) - eval runs sized to the change, so a cycle is not spent on suites it cannot affect: a map from changed paths to eval suites, which `evals/run.py` reads to run only the suites a diff touches; the full set runs before a release and at a milestone close. A GitHub Actions workflow runs every suite on Linux for each pull request, moving full runs off the developer's machine and disk. The agent and contributor instructions (`openspec/config.yaml`, `CONTRIBUTING.md`) say which suites to run when. Only this repository's development workflow changes; nothing an installed project runs.
5. `fix-codex-windows-route` (0.9.3) - #118 the codex route on Windows: codex's own error read from its `--json` event stream first, then the failing flag isolated by repro and fixed. If the fix moves read-only enforcement off the OS sandbox (an ACP transport such as acpx), that is an ADR in the change's design, and the change ships as a minor release instead.
6. `commit-per-task-group` (0.10.0) - #20 `commit_granularity: task | group`: one commit per task group at the group boundary, with `Specwright-Task:` trailers as task evidence, partial-group and code/store-pair recovery, and no rewriting of published history. Independent of the VCS backend.
7. `add-jj-backend` (0.11.0) - #19, jj part: `vcs: git | jj` selects the tool that owns every write across branch, commit, finish, PR and roadmap proof (bookmarks, detached Git HEAD, explicit PR head, conflicts checked before publication), with a stop before any write when jj or a colocated repo is missing. Planning stores keep their own backend, set explicitly.
8. `add-gitbutler-backend` (0.12.0) - #19, GitButler part: `vcs: gitbutler` on the same seam, reusing GitButler's own agent skills; commits targeted to the change's branch, never sweeping other workspace changes, and publication limited to the change's own PR under the fenced account.

## Next: M6 - Packs

Opt-in, per-project domain extensions (#68), additive only: a pack adds phases, checks and skills and never relaxes a gate. The first pack is gamedev, prototyped in a dogfood project before it ships.

## Later

- Unplanned features, placed at a later **close**: #42 stealth mode; #72 a configurable report signal per reviewer in `pr.reviewers`.
- Deferred dogfood check, run when a dogfood project is at a convenient point; it does not block a milestone: #98 (M3) an update with a change in flight. (#86, the M2 agent-merge check, passed in sh1ny/blackgrid#44.)
- Unscheduled `known-gap` issues filed after a milestone is planned are placed into a milestone at the next **close**, or into an earlier change that touches the same code.
- Parked: #9 snapshot pagination beyond 100 items; revisit if large PRs become routine.

## Done

- **M4 - Cost tier** (closed 2026-10-26; PRs #102, #104, #108, #112, #120, #126; releases 0.6.1-0.8.0). All six exit criteria passed. Learned: fifteen gaps were filed during M4 (#109-#125, less the PRs), mostly edge cases that reviews of `fix-deferral-followups`, `bound-pr-scripts` and `exact-eval-grader` found and that were filed as issues instead of fixed in those PRs, plus #118 from a dogfood project, so M5 opens with three gap-fix changes; the codex route still fails on Windows after #95 because a failing run discards codex's own error, so the next fix starts with diagnostics; the Haiku stress run found two wording gaps and one grader false negative and no model limit, so wording tests on the cheap tier are worth keeping; `evals/finish`, added by `fix-deferral-followups` (itself inserted mid-milestone), was not named in the criteria, so M5's criteria name it; and the six suites took about two and a half hours on Windows at about 215 ms per process launch, so M5 cuts launches per test (#127).
- **M3 - Distribution** (closed 2026-10-17; PRs #89, #90, #92, #96; releases 0.4.1-0.6.0). Seven of eight exit criteria passed; the user-verified dogfood update with a change in flight is deferred to #98, by the user's choice, because it can only run once a release is out and waiting for it would hold up M4. Learned: a user-verified check against a published release cannot pass before close, so later milestones list such checks as follow-ups instead of exit criteria; `safe-update-lifecycle` took six fix rounds, four past the limit, with each round finding a new lock or interruption race, so concurrency-heavy changes need race tests in the design, not just in review; the update suite takes about half an hour on Windows because it spawns a process per file operation; and seven gaps were filed during M3 (#91, #93, #94, #95, #97, #99, #100; the last two found by the first attempt at the deferred dogfood check), so M4 again opens with a gap-fix change.
- **M2 - Ship flow** (closed 2026-10-14; PRs #71, #73, #79, #82, #85; releases 0.1.12-0.4.0). Six of seven exit criteria passed; the user-verified dogfood run of the pre-ship review and agent merge is deferred to #86, by the user's choice, because it needs a full change in a dogfood project. Learned: the review-run.sh tests landed in a third suite, `evals/review-routes`, that the criteria did not name, so M3's criteria name all three; nine known gaps were filed during M2 (most found by the pre-ship and Codex reviews before merge), so M3 again opens with a gap-fix change; and graded agent evals must be re-run after late skill edits (the agent-merge evals were re-run at close for that reason).
- **M1 - Hardening** (closed 2026-10-11; PRs #59, #62, #67; releases 0.1.9-0.1.11). Learned: PR-flow gaps surfaced faster than they closed (16 issues filed during M1), and local cross-model reviews before push caught what Codex would have (it found nothing on #67), so M2 opens with two gap-fix changes and makes the pre-ship review a step.
