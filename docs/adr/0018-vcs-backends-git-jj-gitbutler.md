# 0018. Version-control backends: Git, colocated jj and GitButler

- Status: accepted
- Date: 2026-10-30
- Supersedes: 0017

## Context

ADR 0017 made `skills/specwright-pr/scripts/vcs.sh` the one boundary for backend selection, branch state and every version-control write, and accepted `git` or `jj`. Issue #19 asks for GitButler next to jj. A GitButler workspace applies several branches in one working tree at once. Git's HEAD is the synthetic `gitbutler/workspace` commit, or the single applied branch, so HEAD no longer stands for the change. A plain `git commit` or `git checkout` corrupts the workspace. Any `but` command, `but status` included, sets a repository up as a side effect. `but push` always force-pushes, and `but pr` authenticates with GitButler's own forge login, outside ADR 0008's fence. 0017 says the setting "accepts `git` or `jj`" and that only the release tag bypasses its Git-write rule, so adding GitButler contradicts it. This ADR restates 0017 and adds GitButler.

## Decision

- **One seam:** `vcs.sh` owns the branch read and every version-control write for all three backends. Each subcommand probes the selected per-repository backend before reading branch state or writing. The setting is explicit and never inferred from `.jj/` or `.git/gitbutler/`. `vcs` accepts `git`, `jj` or `gitbutler`; `planning_store.vcs` accepts `git` or `jj`. Each defaults to `git` independently, and the store never inherits the code setting. An unknown value stops with `unknown_vcs` and the accepted values.
- **GitButler scope:** `gitbutler` is for the code repository only, with `finish: pr` only. `planning_store.vcs: gitbutler` stops with `unsupported_vcs`, and `vcs: gitbutler` with any other `finish` (absent included) stops with `unsupported_combination`, both before any write in either repository. `merge` and `advance` have no GitButler meaning and stop.
- **Colocated jj, Git reads:** jj is supported only when `.jj/` and the Git work tree share a toplevel. Read-only history, trailers, ranges and tree queries stay on Git for every backend. Specwright never initializes, converts, sets up or tears down a repository.
- **GitButler probe without side effects:** Git reads run first (`.git/gitbutler/` and `gitbutler.project.targetRef` naming `<main>`), and only then `but --version`, from a directory outside the repository, which must report 0.23 or newer. A repository GitButler does not manage stops with `not_managed` before any `but` command runs in it.
- **Git backend refuses a GitButler workspace:** with the `git` backend, a repository GitButler manages stops with `gitbutler_workspace` before any write, whatever HEAD is.
- **Named branch, never HEAD:** on GitButler the caller names the change branch, and `state` reports it by name (applied or not, its tip, and dirty paths split into the change's, unassigned and other branches'). Every range or record that stands for a change's commits (pre-ship range and record key, task evidence, the reviewer's diff, finish's head checks, `release.sh check`) takes the branch name and resolves its tip itself on every call. On Git and jj that tip is HEAD, so their ranges and keys are unchanged; on GitButler a reader without the branch name stops.
- **Working-copy invariant (jj):** the change bookmark points to `@-`; `@` holds only uncommitted work. Moving the working copy carries its edits, and a conflicting carry is rolled back and stops. Merge construction happens off to the side and is reused on retry.
- **Named-path commits (GitButler):** a commit runs `but commit -b <branch>` with the message file and the named paths, never without paths and never by CLI ID. It stops first when a named path belongs to another applied branch, and it checks with Git reads afterwards that the new tip has the old tip as parent, holds the message, touches exactly the named paths that changed, and left every other branch's tip unchanged; otherwise it stops with `commit_mismatch` and leaves the commit for the user.
- **Fetch, pull and push:** a read-only main refresh writes only `FETCH_HEAD` and reads that commit in the same call (jj and GitButler). The jj pull fetches only main after checking fast-forward ancestry. The GitButler pull runs `but pull` only when no other branch is applied and no linked worktree exists, so Specwright never rebases another branch; otherwise it reports `pull_skipped`, and steps that read main afterwards read the fetched remote main. The GitButler push is the fenced `git push origin refs/heads/<b>:refs/heads/<b>`, without force and without setting an upstream; `but push` and `but pr` are never run. A GitButler branch is deleted with `but branch delete` only once the workspace base (`mergeBase` from `but status --json`) holds the merge.
- **Network fence:** jj fetch and push, `but pull` and the GitButler push run through `as.sh` under the GitHub identity fence. `as.sh` fences `but pull` only and refuses every other `but` subcommand and any option selecting another directory or repository. These commands gain no deadline, matching the fenced Git commands outside ADR 0014's scope.
- **Git-write exceptions:** release publication keeps Git for its annotated tag and the tag-specific fetch and push. On GitButler the change branch's push is the one other Git write. No other Specwright write bypasses `vcs.sh`.
- **Recovery and evals:** jj and GitButler state is rebuilt from their own state and Git evidence; no operation journal or stash emulation is added, and debug never stashes on jj or GitButler. Evals run the real pinned tools in short-lived scratch repositories and log Specwright's Git calls to enforce the write boundary. CI downloads each pinned binary and checks its SHA-256 before running it.
- **Undo:** on jj and GitButler, the undo plan restores and moves files in the working copy from Git reads before committing the named paths through the backend; it runs no Git write and is not an atomic Git-index workflow.

## Consequences

Every skill, script and eval that reads branches or writes version-control state uses the backend seam, and every range reader takes the change branch's name. Git history stays the shared evidence format, and Git stays the default. `finish: local` or a planning store on GitButler, stacked branches, `but worktree`, inferring a backend, adding deadlines to these network commands or broadening the Git-write exceptions requires a new decision. 0017's file stays unchanged; its index row is replaced by this ADR's. Reversal cost: medium. Removing GitButler is one backend branch per subcommand plus a settings value, but the named-branch reads and the tip-keyed review records would stay.
