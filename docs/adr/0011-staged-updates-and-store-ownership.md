# 0011. Updates are staged and swapped by a journaled script; a store's schema has one recorded owner

- Status: accepted
- Date: 2026-10-17

## Context
Install is a prompt the agent follows. Its Step 4 deletes each `specwright-*` skill directory and then copies the new one, and replaces the schema in place. Nothing records a partial Step 4, so an interruption shows up only as a missing script at the next skill run, and a store's shared schema is replaced for every project that uses it, including one with a change in flight (#36). ADR 0001 left that consequence open. The download was also `main`, which can hold unreleased work; ADR 0010 now makes release tags permanent, so a tag is a stable thing to install from. `openspec validate` checks delta format only and does not load the schema, so a changed schema can leave a change in flight unusable with no error. `specwright-branch` already serialises store gates with an atomic `mkdir` lock, and ADR 0003 puts local state in a cache and rejects Specwright state files committed in a repo.

## Decision
Updates follow these rules.

- **A script does the file work; the prompt keeps the questions (D1).** `scripts/update.sh` at the repo root runs from the downloaded copy, with subcommands `plan` (read-only), `recover`, `stage`, `swap` and `finish`, each printing one JSON document (ADR 0002). The prompt keeps the targets, settings and schema choice, the `config.yaml` and `specwright.yaml` merges, the Step 7 checks and the `VERSION` stamp. It names its minimum release and the script `interface` it drives, and stops when the download does not match.
- **Stage next to each target, swap with two renames (D2).** Each target directory gets a sibling `.specwright-update-<basename>/` with `new/` and `old/`: target to `old/`, then `new/` to target. A sibling is on the same filesystem and never inside a skills directory, so no harness loads it.
- **A journal in the project, written before each step (D3).** `openspec/.specwright/update.json` starts with `format: 1` and holds `from`, `to`, every target with its state, a manifest (path and SHA-256 of each staged file) and the store role. It is written atomically before the step it records. `recover` discards the staging when the swap has not started, resumes when every staged target still matches the manifest, and otherwise rolls back; a `VERSION` already at `to` leaves only `finish`. This is an exception to ADR 0003's local-state location: the journal describes files in this checkout and the staging next to them is useless without it, so a cleared or foreign cache would orphan them. ADR 0007 set the precedent for such an exception.
- **A store's schema has one recorded owner (D5).** `<root>/openspec/.specwright/STORE` holds two lines, `version: <x.y.z>` and `owner: <id>`. `<id>` is the code repo's `origin` fetch URL as `host/owner/repo` (scheme, userinfo, `.git` and a trailing dot on the host dropped), or `path:<code toplevel>` with no `origin`. `plan` gives the role `none`, `claim` (no `STORE`), `owner` or `other`. A project with role `other` stages only code-side files and is refused when its target's major or minor version differs from `STORE.version`.
- **Only the owner writes the store, and only when it is free.** For `owner` or `claim`, `swap` takes the store's `specwright-gate.lock` before its first rename: it writes a random token into the journal, runs `mkdir`, then writes the lock's `owner` file naming `specwright-update`, this checkout and the token. Under the lock it re-reads `STORE`, checks the store is free (on its main, clean apart from the update's own paths), repeats the in-flight collection, attribution and validation, then swaps the code side, the schema and `STORE` in that order, keeping the old schema in `old/`. A busy store (on a change branch or dirty) stops the update, except that a patch update with a byte-identical schema swaps only the code side. Another project's change in flight refuses the update; a change is this project's when the code repo has a local branch `<prefix>/<change-name>`.
- **The gate-lock token and its recovery.** `recover` takes the lock over only when its `owner` names `specwright-update`, this checkout and the journal's token, and releases it in every outcome. A lock with no `owner` file is shown to the user under the existing confirm-then-remove rule. Any other holder stops `recover`. `specwright-branch` and roadmap show an update's lock, say to rerun the update from that checkout and do not offer removal.
- **`STORE` is a second departure from ADR 0003.** It is a committed per-store Specwright state file, which ADR 0003 rejects in general. It is kept because ownership cannot be derived from git history or GitHub. The install never commits it; the user does, and a transfer of ownership is a manual commit of `STORE`.
- **"Validates" means three checks (D4).** For every change in flight, in a scratch root with the staged schema: `openspec schema validate specwright`, `openspec validate <change>`, and `openspec status --change <change> --json` with no error and no done artifact whose `requires` is missing. A failure refuses the update. The set is re-collected and re-validated in `swap` before the first rename.
- **The update downloads the highest release tag (D7).** Not `main`, unless asked or no tag exists.

**Rejected (D1): Step 4 kept as prompt text with staging rules written out**, because an agent cannot be interrupted at a chosen step in an eval and its rename order would differ between runs. **Rejected: installing `update.sh` into projects as a skill**, because it must come from the new version and a copy in the project would be swapped by itself.

**Rejected (D2): staging in one temp directory and copying into place**, because a copy is not atomic per directory and a temp directory on another drive cannot be renamed into place. **Rejected: a `specwright-current` symlink to a versioned directory**, because Git Bash on Windows creates copies, not links, without developer mode, and harnesses would see the versioned directories as skills.

**Rejected (D3): the journal under `~/.cache/specwright/`**, for the reason above. **Rejected: no journal, inferring state from the staging directories**, because a missing target with both `new/` and `old/` present looks the same whether the swap just started or nearly ended.

**Rejected (D5): any project may update, guarded by in-flight checks**, because it gives no stable answer to who moves the store forward. **Rejected: writing `STORE` in `finish`, after the stamp**, because the new schema would sit beside an old record, so old-version gates pass and two claimers both write the record. **Rejected: swapping the schema on the owner's change branch**, because it would be an uncommitted edit in that change's working tree, which `specwright-commit` stages around by name. **Rejected: attributing a change by a field in its `.openspec.yaml`**, because older changes have none and OpenSpec owns that file's format (ADR 0001).

**Reversal cost.** D1: medium, an interface change bumps `interface`, which older prompts then refuse. D2: low, internal paths removed by `finish`. D3: medium, a file format that lives only while an update is unfinished. D5: high for the `STORE` format and the owner id, since stores keep them; settled by keeping the format to two `key: value` lines a later version can extend.

## Consequences
- An interrupted update ends at exactly the previous or the new version on a rerun, with no staging, journal or lock left. This answers ADR 0001's consequence about #36; ADR 0001 is unchanged.
- A store's schema changes only through its recorded owner, on a free store, under the gate lock. Other projects stop at the gate on a major.minor mismatch and are told to update.
- Changes in flight are validated against the staged schema before any rename; one that fails refuses the update.
- ADR 0003 has two more exceptions: the in-project journal and the committed `STORE`. Both are named here and nowhere else.
- A crashed update leaves the store blocked until it is rerun from the same checkout. That is safer than a half-swapped schema.
- A running agent session keeps old skill text in context; the report tells the user to restart, and nothing detects it.
